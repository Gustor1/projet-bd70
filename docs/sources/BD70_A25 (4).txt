ppt/slides/slide14.xml
Définitions
Collecter
 : c’est à partir de là que naît la donnée, qu’on acquière les informations provenant de l’environnement interne ou externe à l’entreprise.
Stocker
 : dès que l’information est acquise, le système d’information la conserve. Elle doit pouvoir être disponible et doit pouvoir être conservée dans le temps.
Transformer/traiter
 : cette phase permet de transformer l’information et choisir le support adapté pour traiter l’information. Ici ont construit de nouvelles informations en modifiant le fond ou la forme.
Diffuser : 
le SI transmet ensuite l’information dans son environnement interne ou externe.

ppt/slides/slide15.xml
Définitions
Le SI est un outil de communication entre les différents services d’une entreprise et a un rôle opérationnel et stratégique (notamment en simplifiant le pilotage de l'entreprise)
Le système d'information comporte plusieurs composantes ou ressources (personnel, logiciels, matériels, données, processus, etc.) mais dans cette UV nous aborderons plus spécifiquement la dimension logicielle

ppt/slides/slide16.xml
Définitions
Le progiciel de gestion intégrée (PGI) ou Enterprise Resource Planning (ERP) est la principale composante logicielle du SI
Il s'agit du logiciel qui permet de gérer l'ensemble des processus d'une entreprise en intégrant l'ensemble de ses fonctions, dont la gestion des ressources humaines, la gestion comptable et financière, l'aide à la décision, mais aussi la production, la vente, la distribution, l'approvisionnement et le commerce électronique
Un ERP est adapté à une entreprise, leur conception nécessite une bonne intégration avec l'ensemble du système d'information d'une entreprise et une bonne compréhension des processus de celle-ci

ppt/slides/slide22.xml
Introduction
La base de données hiérarchiques (
obsolète
)
Les données sont organisées selon une structure arborescente : par exemple dans des dossiers avec des sous-dossiers, avec eux-mêmes des sous-dossiers, etc.
La structure est vite limitée, exemple :
Hiérarchie 
Musique/Artiste/Album
, mais comment récupérer rapidement la liste des albums correspondant à un style musical ?
Changer la hiérarchie en Musique/Style/Artiste/Album, mais que se passe-t-il si un groupe a composé des albums dans plusieurs styles ? Et si plusieurs artistes ont participé à un même album ?

ppt/slides/slide25.xml
Introduction
Orienté agrégats
Données souvent représentées sous la forme d’associations clé/valeur (comme un dictionnaire)
Gèrent un très gros volume de données (Big Data)
Facilement distribuables sur plusieurs serveurs
Mais pas de relations entre différentes entités
Exemple : MongoDB (base orientée document)
Orienté graphes
Données représentées sous la forme d’un graphe
Gèrent plus efficacement les relations entre les entités
Capable de gérer des gros volumes de données
Les agrégations et les opérations sont moins performantes (exemple : extraire d’une base la somme des factures)

ppt/slides/slide27.xml
Base de données relationnelles
Le système de gestion de base de données relationnelle (SGBDR)
Gère les bases de données
Stocke les informations dans les bases de données
Fournit une interface et un langage de requête pour accéder aux données de la base
Peut fonctionner sur le schéma Client-Serveur (les données sont mises à disposition de plusieurs applications, exemple MySQL), en local (les données sont stockées pour une application, exemple SQLite), en mémoire (les données sont stockées dans la RAM, exemple H2)

ppt/slides/slide32.xml
Base de données relationnelles
Jusqu'ici une base de données n'est pas très différente d'un tableur
La particularité d'une base de données relationnelle est de pouvoir définir des relations entre les enregistrements de différentes tables
Pour ce faire, un champ doit pouvoir être identifié de façon unique et doit pouvoir référencer un champ d'une autre table de façon unique

clé 
est un attribut ou un identifiant 
unique 
associé à un enregistrement (deux enregistrements ne peuvent pas avoir la même valeur pour la clé)

clé primaire

ppt/slides/slide41.xml
Base de données relationnelles
Types de relation :
1:1 : un élément de la table A est relié à un seul élément de la table B
1:N : un élément de la table A peut se rapporter à plusieurs éléments de la table B (cf. exemple précédent)
N:M : un élément de la table A peut se rapporter à plusieurs éléments de la table B et un élément de la table B peut se rapport à plusieurs éléments de la table A (nécessite l'utilisation d'une table de jointure)

ppt/slides/slide56.xml
Analyseur de requêtes
L’
analyseur de requêtes

Analyse lexicale : découpage de la requête en

Vérification des autorisations

L’
optimiseur de requêtes 
permet d’améliorer la rapidité d’exécution d’une requête, il repose sur les mécanismes suivants :
Sélection parmi les plans d’exécution possibles
Ré-écriture
 de requête
Utilisation d’index
Sélection d’algorithme de jointure
Gestion de la concurrence (limitation du blocage des ressources)

ppt/slides/slide58.xml
Plan d’exécution
Le 
plan d’exécution
 issu de l’analyseur et de l’optimiseur de requête décrit comment les données seront accédées, notamment : 
Dans quel ordre les données seront récupérées (si elles proviennent de plusieurs tables)
Comment les liens entre les données seront réalisés, sur la base de quels index
La plupart des SGBDR proposent des fonctionnalités de visualisation du plan d’exécution, cela permet au développeur d’identifier d’éventuels problèmes d’optimisation des requêtes

ppt/slides/slide59.xml
Gestionnaire de transactions
Une 
transaction
 est une unité d’exécution composée d’une ou plusieurs opérations d’accès à la BDD (consultation ou mise à jour) devant être exécutées solidairement (soit toutes les requêtes de la transaction sont exécutées, soit elles sont toutes annulées) – elles sont notamment utilisées pour gérer les accès concurrent à la base
Le 
gestionnaire de transactions 
intervient après l’optimiseur de requête pour exécuter les requêtes sous la forme d’une transaction
59

ppt/slides/slide60.xml
Transaction
Une 
transaction
 est une unité d’exécution composée d’une ou plusieurs opérations d’accès à la BDD (consultation ou mise à jour) devant être exécutées solidairement/atomiquement (soit toutes les requêtes de la transaction sont exécutées, soit elles sont toutes annulées) – elles sont notamment utilisées pour gérer les accès concurrent à la base

ppt/slides/slide129.xml
Index
Pourquoi ne pas mettre des indexes partout ?
Un index possède un 
coût en espace mémoire 
(ça correspond virtuellement à la création d’une table supplémentaire contenant autant d’enregistrements que la table indexée)
Un index introduit un

Le concept de

ppt/slides/slide161.xml
Propriétés des transactions
Les transactions sont régies par le propriétés 
ACID
 :
Atomicité : 
Le résultat d'une transaction peut être soit un succès total, soit un échec total. L'ensemble de la transaction doit être annulé si l'une de ses parties échoue.
Cohérence : 
Les transactions maintiennent les contraintes d'intégrité en faisant passer la base de données d'un état valide à un autre.
Isolation : 
Les transactions simultanées sont isolées les unes des autres, ce qui garantit l'exactitude des données.
Durabilité : 
Une fois qu'une transaction est validée, ses modifications restent effectives même en cas de défaillance du système.

Sécurité des accès
Une base de données contient généralement des informations personnelles et sensibles (notamment le nom des utilisateurs, leurs emails, leurs adresses personnelles, etc.)
La sécurisation des accès à la base est critique : choisissez toujours la politique la plus stricte possible mais suffisante pour permettre de manipuler la base
De manière générale :
Seul l’administrateur de la base doit pouvoir en modifier la structure
L’application qui se connecte à la base doit être autorisée sur la base de son IP, elle possède un nom d’utilisateur propre avec un mot de passe qu’elle est la seule à connaître (
jamais de transmission du mot de passe de la BDD sur le réseau
), elle doit avoir le droit de consulter et modifier les données des bases nécessaires à son fonctionnement (et uniquement de ces bases)
Tous les autres accès à la base sont interdits

Sauvegarde et redondance
Sauvegarde :
Le contenu de la base doit être sauvegardé à intervalles réguliers afin de pouvoir éventuellement consulter ou restaurer un état antérieur : il s’agit d’un export des données dans un fichier SQL (éventuellement une fois par jour, lors des périodes de creux de l’activité de la BDD)
Redondance :
La sauvegarde n’est pas toujours suffisante : par exemple, si un site de e-commerce perd trace des commandes passées dans les dernières 24h les conséquences peuvent être dommageables pour les clients
Une stratégie de redondance permet de dupliquer la base sur N serveurs distincts afin de pallier les défaillances d’un des serveurs

Optimisation de la base :
La base doit être normalisée
Les index doivent être clairement définis (clés primaires, clés étrangères, ou tout autre champ sur lequel des requêtes sont fréquemment faites)
Les déclencheurs/triggers doivent être utilisés avec parcimonie
Optimisation des requêtes :
Ne récupérer que les champs nécessaires
Limiter le nombre d’enregistrements récupérés (il n’est pas toujours nécessaire de récupérer tous les enregistrements d’une table, on peut aussi les récupérer 10 par 10 au fur et à mesure)
Eviter les sous-requêtes, les jointures de type CROSS JOIN
Ne pas effectuer des traitements qui enchaînent les requêtes dans des boucles

Concepts de bases HTTP/HTML
Lorsqu’on souhaite afficher une page Web, le navigateur envoie une requête HTTP au serveur
Cette requête est de type GET et elle contient en information l’URL que l’utilisateur cherche à atteindre et éventuellement des paramètres saisis dans l’URL sous la forme « ?nomDuParam1=valeurDuParam1&nomDuParam2=valeurDuParam2 »
Le serveur interprète cette requête et retourne la page demandée à l’utilisateur
Lorsqu’on envoie un formulaire, le navigateur envoie (généralement) une requête de type POST avec les valeurs du formulaires en paramètre (le traitement effectué par le serveur est identique à celui de la requête GET)
